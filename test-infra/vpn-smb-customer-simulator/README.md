# Simulated customer VPN + SMB repository

This directory contains a disposable, production-representative customer
environment used to validate TableScope's **Isolated Data Plane + Customer VPN**
file import workflow.

## Contents

| Path | Purpose |
|---|---|
| `terraform/` | AWS VPC, subnet, IGW, EIP, EC2, security groups, flow logs. |
| `compose/` | `docker compose` stack for strongSwan and Samba (host-networked). |
| `fixtures/` | Deterministic test files generated by `scripts/generate-fixtures.py`. |
| `scripts/` | Fixture generator, strongSwan config renderer, EC2 user data. |

## IP address plan

| Network | CIDR | Notes |
|---|---|---|
| Simulated customer VPC | `10.250.0.0/16` | Must not overlap any TableScope VPC or tenant Docker subnet. |
| VPN gateway / public subnet | `10.250.10.0/24` | EC2 host, strongSwan and Samba run with `network_mode: host`. |
| Samba share | `//<gateway-ip>/repository` | The `dperson/samba` container binds SMB3 TCP/445 to the host IP. |

Because both strongSwan and Samba use the host network, the SMB repository is
natively reachable from the IPsec tunnel without extra container-to-container
routing.

## Generating fixtures

```bash
pip install -r scripts/requirements.txt
python3 scripts/generate-fixtures.py --output fixtures
```

`fixtures/tablescope-inbound` contains the share root.
`fixtures/fixture-manifest.json` lists every file, its size, and SHA-256 hash.
No live malware sample is committed; the EICAR test string is generated on
demand.

## Deploying the simulator

```bash
cd terraform
export AWS_REGION=us-west-1
export TF_VAR_run_id="$(date +%s)"
terraform init
terraform plan -out=tfplan
terraform apply tfplan
```

After `terraform apply`, output `customer_gateway_public_ip` is the Elastic IP
to use as the customer gateway IP in TableScope's tenant VPN configuration.

The EC2 user data (`scripts/gateway-user-data.sh`) installs Docker, starts an
`sshd` service, starts the Samba container, and creates a systemd unit that will
start strongSwan once its configuration is rendered.

## Rendering the VPN config

After the TableScope tenant VPN connection is created, run on the gateway host:

```bash
CUSTOMER_GATEWAY_IP=<simulator EIP> \
CUSTOMER_LAN_CIDR=10.250.10.0/24 \
REMOTE_CIDRS=<TableScope shared VPC CIDR>,<test tenant VPC CIDR>,172.30.0.0/16 \
python3 scripts/render-vpn-config.py \
  --vpn-connection-id <vpn-xxx> \
  --region us-west-1 \
  --format ipsec \
  --output-dir /etc
```

This writes `/etc/ipsec.conf` and `/etc/ipsec.secrets` (mode `0600`) using the
classic starter/stroke format that the `alpine:3.18` strongSwan container
expects. `REMOTE_CIDRS` must include both the TableScope shared VPC CIDR and
`172.30.0.0/16` (or the specific tenant Docker subnet) so that SMB traffic
after Docker MASQUERADE matches the phase-2 selector.

Then start or restart strongSwan:

```bash
# If using the systemd units installed by user data:
systemctl restart tablescope-samba

# Or with docker compose:
cd compose
SAMBA_PASSWORD=<generated> \
STRONGSWAN_CONFIG_DIR=/etc \
docker compose up -d
```

## Security

- `ipsec.conf` / `ipsec.secrets` contain pre-shared keys. They are created with
  `0600` and are never checked into git.
- The SMB container binds only to the host network; the AWS security group
  restricts TCP/445 to the VPN source CIDRs.
- The repository volume is mounted read-only.
- AWS flow logs are captured to a 1-day CloudWatch log group.
